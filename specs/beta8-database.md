# 베타 시즌 8 공용 계정·데이터베이스

2026-10-22 · 사용자 요구사항 확정 · 공용 서비스 도입 전 설계

베타에서 먼저 [로컬 로그인 시험](beta8-login-trial.md)을 구현·검증했다. 아래 메인·베타 공용 DB 도입과 별도 단계이며 기존 메인 데이터는 변경하지 않았다.

## 확정 범위

- 아이디·비밀번호로 회원가입·로그인한다.
- 메인과 베타는 동일한 계정과 영구 저장 데이터를 사용한다.
- 캐릭터·스킨 보유/장착, 코인·크레딧, 캐릭터별 레벨·트로피, 일일/이벤트 진행도, 전적·랭킹을 저장한다.
- 시즌·모드별 전적은 공용 계정 아래 구분해서 보관한다. 두 화면이 같은 전체 전적을 읽되 KNOCKOUT과 쇼다운 기록 등을 섞지 않는다.
- 다른 기기에서도 같은 계정으로 로그인하면 저장 데이터를 불러온다.
- PHP 도입은 필요 없다. 기존 JavaScript 게임과 Cloudflare Worker에 연결한다.

## 현재 구조에서 달라지는 부분

현재 메인의 `skullCreekAccounts`/`skullCreekAccount`와 베타의 `colorsBetaSeasonTest`는 브라우저 저장소다. 메인의 기존 로그인은 로컬 아이디 대조이며 서버 비밀번호 인증이 아니다. `party/server.js`의 `LeaderboardStore`는 서버 영구 저장을 사용하지만, 클라이언트가 보낸 트로피를 받는 현재 방식은 검증된 경쟁 랭킹의 근거로 사용할 수 없다.

기존 Cloudflare 배포에 D1 SQL 데이터베이스를 연결하는 방향을 기본안으로 한다. 회원가입·인증·저장은 Worker API를 통해서만 수행하고, 브라우저에는 DB 접근 권한을 전달하지 않는다. 현재 Wrangler 설정과 실제 원격 리소스는 이 설계 작업에서 변경하지 않는다.

## 공용 데이터 모델

| 데이터 | 저장 단위 | 규칙 |
|---|---|---|
| 계정 | 고유 내부 계정 ID | 로그인 아이디의 대소문자/중복 정책을 서버에서 일관되게 적용 |
| 인증 | 비밀번호 해시·로그인 세션 | 평문 비밀번호 저장 금지, 서버 검증, 세션 만료·로그아웃 |
| 재화 | 계정별 잔액 + 변경 원장 | 구매·지급을 서버 트랜잭션으로 반영, 중복 요청 1회 처리 |
| 보유 목록 | 계정 + 종류 + 아이템 ID | 메인·베타 공통, 획득 근거 기록, 중복 보유 방지 |
| 장착/선택 | 계정별 설정 | 영구 보유 여부와 캐릭터 일치 검증 |
| 성장 | 계정 + 캐릭터 ID | 레벨·트로피와 성장 재료를 공용으로 관리 |
| 진행도 | 계정 + 이벤트/날짜 ID | 같은 보상 재수령 방지, 서버 날짜 기준 |
| 경기 | 고유 경기 ID + 참가 계정 | 시즌·모드·종료 사유·결과·검증 상태 기록 |
| 전적/랭킹 | 검증된 경기 결과의 집계 | 클라이언트가 임의로 제출한 승수·트로피를 직접 수용하지 않음 |
| 이전 기록 | 계정 + 이전 작업 ID | 이전 전 백업·출처·완료 시점·중복 처리 여부 보존 |

스키마는 버전별 마이그레이션으로 관리한다. 계정 ID는 닉네임과 분리하고 닉네임 변경으로 소유 데이터가 달라지지 않게 한다.

## 시험 콘텐츠와 영구 보유

공유 대상은 영구 데이터다. 베타의 무료 시험 캐릭터·스킨·시험용 초기 재화는 정식 획득과 별도로 표시하는 시험 권한으로 처리한다. 베타를 여는 것만으로 메인의 영구 보유 목록이나 재화가 증가하면 안 된다. 베타 전용 아이템도 영구 획득한 경우 공용 계정에 보관하되 지원하는 화면에서만 사용한다.

이는 현재 베타의 `loadBetaState()`가 시험 콘텐츠를 자동 지급하는 구조를 바꿔야 한다는 뜻이다. 실제 공용 저장 연결 전에 반드시 처리한다.

## 기존 데이터 이전

1. 기존 로컬 저장을 자동 삭제하거나 초기화하지 않는다. 이전 직전 원본 백업을 만든다.
2. 기존 메인 계정과 베타 저장을 읽어 보유 목록·재화·성장·전적의 차이를 보여준다.
3. 같은 로컬 아이디만으로 기존 서버 계정의 소유권을 인정하지 않는다. 서버 계정 인증 후 해당 계정으로 가져온다.
4. 보유 목록은 정식 획득과 시험 지급을 구분한다. 서로 다른 잔액과 진행도는 무조건 합산하거나 단순 최댓값으로 합치지 않는다. 출처를 표시하고 이전할 값을 확정한다.
5. 출처를 검증할 수 없는 과거 로컬 전적은 과거 기록으로 보존하되 새로운 검증 랭킹에 소급 반영하지 않는다.
6. 동일한 이전 작업은 한 번만 반영한다. 서버 반영 성공을 확인하기 전 원본을 덮어쓰지 않는다.
7. 두 기기 또는 메인·베타의 동시 저장은 버전 충돌로 감지한다. 오래된 전체 저장으로 최신 잔액·보유 목록을 덮어쓰지 않는다.

## API와 클라이언트 연결

- 인증: 가입, 로그인, 로그아웃, 현재 계정 확인. 서버 측 로그인 시도 제한과 세션 폐기를 제공한다.
- 공용 저장: 계정 조회, 선택/장착 변경, 구매, 보상 수령, 성장. 서버가 허용된 명령만 처리한다.
- 경기: 서버가 발급한 경기 ID로 참가자를 식별하고 검증된 종료 결과를 1회 반영한다. 현재 호스트 중계만으로 결과를 신뢰할 수 있는지 별도 검증한다.
- 랭킹: 서버 집계를 읽는다. 기존 공개 랭킹 POST를 새 경쟁 랭킹의 갱신 경로로 사용하지 않는다.
- 메인과 베타는 같은 API 클라이언트와 저장 규칙을 사용한다. 각 화면에 다른 저장 객체를 병렬로 유지해 잔액이 갈라지는 구조를 만들지 않는다.
- 저장 실패 시 성공으로 표시하지 않고 재시도 상태를 보여준다. 오프라인 로컬 시험 경기는 경쟁 랭킹에 자동 반영하지 않는다.

## 인증 구현 및 출시 전 결정

검증된 비밀번호 인증 라이브러리와 서버 실행 환경을 먼저 선택한다. 직접 만든 암호화 방식은 사용하지 않는다. 비밀번호는 서버에서 해시 처리하고 로그·백업·응답에 포함하지 않는다. HTTPS, 만료되는 세션, 출처 제한과 요청 위조 방어를 함께 검증한다.

이메일을 수집하지 않는 아이디·비밀번호 방식이므로 비밀번호 분실 시 복구 방식은 출시 전에 정한다. 복구 코드 등 소유권을 증명할 수 있는 수단 없이 아이디나 닉네임만으로 비밀번호를 바꾸지 않는다.

## 구현 순서와 완료 기준

1. 로컬 DB 스키마·인증 API: 가입·중복 아이디·틀린 비밀번호·세션 만료·로그아웃·다른 계정 데이터 접근 차단 검사.
2. 공용 계정 API·두 화면 연결: 같은 계정의 잔액·보유·진행도가 일치하고 새로고침·다른 브라우저에서도 복원되는지 확인.
3. 이전 화면: 원본 백업, 충돌 표시, 재화 중복 방지, 실패 시 원본 유지, 같은 이전의 재실행 검증.
4. 검증된 경기 결과·랭킹: 결과 재전송·위조·중도 종료·동시 반영을 검사하고 집계 일치를 확인.
5. 별도 시험 DB에서 브라우저 통합 검증 후 원격 서비스에 적용. 실제 DB 생성·배포·이전 성공은 원격 확인 후에만 완료로 기록한다.

현재 로컬 베타에 새 인증과 계정별 시험 저장을 구현했다. 서비스 DB 생성, 원격 인증 배포, 메인·베타 저장 통합 및 기존 데이터 이전은 아직 수행하지 않았다.
