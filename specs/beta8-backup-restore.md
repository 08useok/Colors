# 베타 계정 DB 백업·복원 검증

검증일: 2026-10-29 (한국 시간). 현재 로컬 계정 서버 SQLite 대상이며 메인 이식·배포는 하지 않았다.

## 결과

- SQLite 온라인 백업으로 실행 중인 WAL 내용까지 일관된 복사본 생성. 원본 연결은 읽기 전용.
- 모든 사용자 테이블의 행 수·내용 해시 대조, 무결성·외래키 검사 통과.
- 복사본을 별도 HTTP 서버에서 열고 시험 계정·저장·복구 코드·경기 기록 생성.
- 별도 서버 프로세스 종료·재시작 후 기존 세션과 비밀번호 로그인, 저장 버전·진행도 유지 확인.
- 이후 재화와 수령 목록을 변경한 뒤 서버 종료. 이전 체크포인트를 새 복원 파일로 복사해 모든 테이블이 일치하는지 검사.
- 복원 파일에서 로그인 후 재화·퀘스트·수령 목록·복구 코드 등록 상태·저장 버전 복원 확인.
- 랭킹 8.625점 유지, 동일 경기 재전송의 중복 처리 확인.
- 실제 원본 DB의 모든 테이블은 시험 전후 내용이 동일. 원본 백업 파일 SHA-256도 동일.
- 모든 시험 서버 프로세스 종료. 백업과 시험 복사본은 Git 제외 폴더 `.local/backups/`에 보관.

[검사 원본](beta8-backup-restore-verification.json)

실제 백업: `.local/backups/20261029T064902414449Z/beta-auth.sqlite`. 같은 폴더의 `manifest.json`에 생성 시각·파일 해시·테이블 대조 결과가 있다. 계정 인증 자료를 포함하므로 공개 업로드하지 않는다.

## 재실행

프로젝트 루트에서 `python tools/backup-beta-database.py`를 실행하면 새 날짜 폴더에 백업을 만든다. 이 PC에서는 기본 Python 대신 번들 Python 실행 경로를 사용했다.

출력된 백업 경로를 `node tools/test-beta-backup-restore.mjs <백업 절대 경로>`에 전달하면 별도 복사본으로 HTTP 서버 재시작과 복원을 검증한다. 시험 프로그램은 원본 백업을 복원 대상으로 덮어쓰지 않는다.

## 실제 복원 시 순서

1. 계정 서버에 쓰는 모든 프로세스를 종료한다. 진행 중 지급·기록을 멈추고 장애 시점 데이터도 보존한다.
2. 현재 DB와 남아 있는 같은 이름의 WAL·SHM 파일을 함께 별도 보존한다. 새 DB에 이전 WAL·SHM이 섞이지 않게 한다.
3. 무결성과 백업 해시를 확인한 스냅샷을 서버가 사용할 DB 경로에 놓는다. 실행 중인 DB 위에 덮어쓰지 않는다.
4. 서버를 시작하고 로그인·저장 버전·진행도·보상·전적·랭킹을 확인한다. 복원 시점 이후 데이터는 별도 비교·복구 대상으로 남긴다.

위 절차의 실제 원본 교체는 이번에 실행하지 않았다. 운영 복원은 백업 이후 진행 손실 범위를 확인한 뒤 수행한다.

## 범위 밖

브라우저 localStorage의 메인·게스트 진행도, 공개 운영 환경, 메인·베타 공유 계정 이관은 별도 백업·검증이 필요하다. 이번 서버 DB 복원을 전체 게임 저장 복원 완료로 해석하지 않는다. 백업은 같은 PC에 있으므로 PC·디스크 고장 대비 외부 보관은 별도다.
